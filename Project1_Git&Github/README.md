## 🏗️ How the Project Works

1. Your team creates a separate repository containing the actual project code.
2. Build and test the project together using Git and GitHub.
3. Deploy the project and confirm the live link works.
4. The Tech Lead forks the central `projects` repository.
5. In the fork, update only your team's row in `project1_git&github/README.md`.
6. Create a team-specific submission branch and open a Pull Request to the central repository.
7. Wait for the instructor/senior to review and merge the PR. **Do not merge your own PR.**

## 👑 Team Roles

### Team Leader / Tech Lead
The person named in each team section is the designated leader for this project. They may coordinate task allocation and submission; the team can contact the instructor if a change is needed.
- Create/manage the team's project repository.
- Coordinate work and ensure the code is pushed to GitHub.
- Ensure the project is deployed and both links work.
- Fork the central repository, update the submission registry, and open the PR.

### Team Members
- Contribute to the project and coordinate with the Tech Lead.
- Use Git for version control and make meaningful commits.
- Push changes to the team's repository using the team's agreed workflow.

## 📌 Rules — Read Before Starting

- ❌ Do **not** add your project code to the central repository.
- ❌ Do **not** create a folder for your whole project inside the central repository.
- ❌ Do **not** ask every team member to edit the central submission registry.
- ❌ Do **not** change another team's row or team details.
- ❌ Do **not** merge your own Pull Request unless explicitly instructed.
- ✅ Only the Tech Lead (or one designated submitter) should update the team's registry row and create the submission PR.

## 🛠️ Team Workflow

### Step 1 — Create your team's repository

Create a public GitHub repository using the exact suggested name for your team:

```text
<your-team-slug>-git-project
```

Examples:
```text
stack-squad-git-project
binary-bandits-git-project
pointer-patrol-git-project
```

The repository should contain your actual project files and a clear `README.md`.

### Step 2 — Clone the repository

```bash
git clone <YOUR-TEAM-REPOSITORY-URL>
cd <YOUR-TEAM-REPOSITORY>
```

### Step 3 — Create a work branch

Do not make all changes directly on `main`.

```bash
git checkout -b feature/project-page
```

Use a descriptive branch name relevant to the task, such as `feature/homepage` or `fix/mobile-layout`.

### Step 4 — Stage, commit, and push your work

```bash
git status
git add .
git commit -m "feat: add project homepage"
git push -u origin feature/project-page
```

Use meaningful commit messages that explain the change. Avoid vague messages such as `update`, `changes`, or `done`.

### Step 5 — Deploy your project

Deploy the completed project. GitHub Pages is suitable for many static websites.

Your submission must include both:
- **Live Project URL** — the deployed version
- **Source Code URL** — your team's GitHub repository

Open both links before submitting to confirm they work.

### Step 6 — Fork the central repository

Open the central `projects` repository and click **Fork**. In your fork, open:

```text
project1_git&github/README.md
```

### Step 7 — Update only your team's registry row

Find the **Submission Registry** table at the end of this README. Update only the row matching your assigned team name. Use the pre-assigned Team Leader / Tech Lead's name, along with member names, live URL, and source-code URL.

### Step 8 — Create your team-specific submission branch

Use the branch assigned to your team in the **Assigned Teams** section above. For example:

```bash
git checkout -b submission/stack-squad
```

### Step 9 — Commit and push the registry update

```bash
git add "project1_git&github/README.md"
git commit -m "docs: submit Stack Squad project"
git push -u origin submission/stack-squad
```

Replace `Stack Squad` and `stack-squad` with your team's exact assigned name and slug.

### Step 10 — Open a Pull Request

Create a PR from your fork to the central `projects` repository.

Use this title format:

```text
docs: submit <Your Team Name> project
```

Include the following in the PR description:

```markdown
## Team Submission

### Team Name
<Your exact assigned team name>

### Tech Lead
<Name>

### Members
- <Member 1>
- <Member 2>
- <Continue until all team members are listed>

### Live Project
<Working deployed URL>

### Source Code
<Team GitHub repository URL>

### Checklist
- [ ] Team repository created
- [ ] Project code pushed
- [ ] README added
- [ ] Project deployed
- [ ] Live URL tested
- [ ] Source-code URL tested
- [ ] Correct registry row updated
```

### Step 11 — Wait for review

The instructor/senior will review the PR. If changes are requested, update the same branch, commit, and push again. The existing PR will update automatically. Do not create a duplicate PR or merge it yourself.

- [ ] Project code is pushed with meaningful commits.
- [ ] The repository has a clear `README.md`.
- [ ] The project is deployed and the live URL works.
- [ ] The source-code URL works.
- [ ] The assigned Team Leader / Tech Lead is identified.
- [ ] The correct team row is updated in the submission registry.

- [ ] The PR has been reviewed and merged by the instructor/senior.

> **Your team's repository contains your CODE.**

```text
CENTRAL PROJECTS REPOSITORY

```
